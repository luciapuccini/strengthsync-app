# PRD: Retire the Temporal integration in favor of the Cloudflare Workflow

## Problem Statement

StrengthSync currently runs two parallel workflow systems. The legacy Temporal stack (a self-hosted worker and workflow-start API on a local machine, reached from the Cloudflare Worker through a Cloudflare Tunnel, with Docker Compose packaging and its own env/secrets files) duplicates what the new in-Worker Cloudflare Workflow already does. This costs real operational burden: a local machine must stay up, a tunnel must be configured, secrets must be maintained in two places, and every workflow change lands in two implementations. It also costs cognitive burden: docs describe both systems, the UI carries dead code paths, and new work must reason about which runtime is authoritative. The "Complete week" flow already runs entirely on the Cloudflare Workflow; only the on-demand "Generate plan" button still depends on Temporal, which blocks deleting it.

## Solution

Retire Temporal completely in a single sweep and make the Cloudflare Workflow the only workflow runtime. The on-demand "Generate plan" feature is dropped for now — it will return later, rebuilt natively on Cloudflare Workflows. No new tests are written for the Cloudflare workflow in this pass; the work is pure deletion plus the minimum adaptation needed to keep the remaining test suite green. The migration also left two agent runtimes: the legacy `@strengthsync/agent` service package (consumed only by the Temporal worker) and the in-Worker `apps/api/src/agent`. The legacy package is deleted in the same sweep, including its `LlmCallRecorder` contract — when LLM tracing returns, the recorder will be redefined fresh against the in-Worker runtime. All Temporal-specific observability boilerplate (LLM call recorders, Braintrust integration, manual eval harness) is deleted along with the worker package. Documentation is updated so the written architecture matches the deployed one.

## User Stories

1. As the developer, I want a single workflow runtime, so that every workflow change is made once and reasoned about once.
2. As the developer, I want to delete the workflow worker package, so that no local machine deployment is required for the product to function.
3. As the developer, I want to delete the Cloudflare Tunnel and Docker Compose setup, so that there is no local infra to boot, monitor, or keep secrets for.
4. As the developer, I want the API to stop proxying workflow-start requests, so that the Worker has one less external dependency and failure mode.
5. As the developer, I want the internal command endpoints removed, so that the Worker's attack surface and auth model shrink to public routes plus the workflow trigger.
6. As the developer, I want the shared domain package trimmed to what the Cloudflare path actually uses — contracts and the coach module's dead prompt-building surface — so that the package documents reality.
7. As the developer, I want the persistence package's legacy command surface removed, so that only the repository functions the Cloudflare workflow calls remain.
8. As the developer, I want Temporal observability boilerplate (LLM recorders, Braintrust) deleted, so that no dead instrumentation config is carried forward.
9. As the developer, I want the manual LLM eval harness deleted with the worker package, so that I don't maintain evals for code that no longer exists.
10. As the developer, I want environment variable examples scrubbed of Temporal, tunnel, and internal-service secrets, so that setup docs and env files only list variables that still do something.
11. As the developer, I want CI, lint boundaries, task-runner config, TypeScript project references, root scripts, and Worker route config to stop referencing the deleted packages, so that tooling reflects the monorepo as it is.
12. As the developer, I want the README and architecture docs to describe only the Cloudflare Workflow architecture, so that future-me and AI agents are not misled by stale Temporal instructions.
13. As the developer, I want existing public-API tests to keep passing after the internal endpoints are deleted, so that the deletion doesn't reduce confidence in the remaining system.
14. As the developer, I want tests that exclusively cover deleted surfaces removed in the same pass, so that the suite contains no tests of dead code.
15. As the coach using the tracker UI, I want the "Generate plan" button gone, so that I never trigger a flow backed by infrastructure that no longer exists.
16. As the coach, I want the "Complete week" button to keep working unchanged, so that weekly progression and automatic plan turnover continue without interruption.
17. As the coach, when a client has no current week, I want a clear empty state without broken actions, so that I understand plan generation is temporarily unavailable.
18. As the developer, I want the cleanup verified with the full existing toolchain (install, lint, typecheck, tests, Worker dry-run deploy), so that the merge is provably safe.
19. As the developer, I want the legacy `@strengthsync/agent` package deleted, so that `apps/api/src/agent` is the single agent runtime and no dead recorder contract is carried forward.
20. As the developer, I want UI state code orphaned by the button removal (the tracker refresh action and the inert complete-week cooldown) deleted with it, so that the store contains no actions nothing can trigger.
21. As the developer, I want the domain coach module reduced to the schemas and rules the Cloudflare workflow imports, with the workflow's deep relative imports normalized to package imports, so that package boundaries and lint rules actually bind.

## Implementation Decisions

- **Single runtime:** The Cloudflare Workflow (`StrengthsyncWorkflow`, weekly progression with plan-turnover branch) becomes the only workflow system. Its trigger route, binding, and UI client are untouched by this work except for removing dead commented code around them.
- **Worker package deletion:** The entire Temporal worker/start-API package is deleted, including its Temporal client and launcher, both Temporal workflows and all activities, the Hono start API, its tests, the LLM call recorders and Braintrust recorder, the manual Braintrust eval harness, and the Dockerfile.
- **Legacy agent package deletion:** `services/agent` (`@strengthsync/agent`) is deleted in the same pass — its only consumers are the worker package's activities, recorders, and eval harness. This removes the duplicated structured-generation runtime and the `LlmCallRecorder`/`WorkflowLlmContext` contract. Decided: the recorder contract is not preserved; when Braintrust tracing is re-wired it will be defined fresh inside `apps/api/src/agent`, and `docs/architecture/evals.md` and `docs/mvp_scope.md` are updated to say so. References in `eslint.config.js` (workspace list, boundary rules, and the `apps/api` allow-list entry that is stale even today), the root `tsconfig.json` project references, and `pnpm-workspace.yaml` build allowances are removed with it.
- **API deletion:** The workflow-proxy routes (which forwarded browser requests through the tunnel) and the internal command routes (which served Temporal activities) are deleted, along with the service-secret middleware, the proxy/lifecycle test files, and the associated app configuration fields and environment variable plumbing.
- **Persistence deletion:** The legacy internal command repository (idempotent commands keyed by workflow id, built for Temporal activity retries) is deleted, including its context-query functions (`getWeeklyContext`, `getPlanGenerationContext`) whose only callers were the internal routes. The newer repository functions used directly by the Cloudflare workflow remain the sole persistence surface. Shared helpers used by the remaining plan repository stay in place despite their legacy module name; the `findWeekByWorkflowId` helper in the same file has no surviving caller and is removed. Tests covering only the deleted repository are removed — including `plan-generation-context.test.ts`, whose name does not say "internal". The kept cases in the broader repository test file currently seed through the legacy deleted commands, so they are re-seeded through the remaining repository functions (the same adaptation as the API testkit), not merely stripped. Stale Temporal wording in schema comments (`workflow_id` column docs) is corrected without changing the columns themselves.
- **Domain trimming:** Workflow status/start schemas, workflow input/result schemas, the browser-facing start bodies, the internal command schemas, and the context-query schemas (`WeeklyContextSchema`, `PlanGenerationContextSchema`) are removed from the domain contracts, along with their schema tests. The generated-plan input and activate-generated-plan command contracts remain, because the Cloudflare plan-turnover branch uses them. The coach module is reduced to what the Cloudflare workflow actually imports (`COACHING_RULES`, the week-analysis and next-week/profile/history schemas and types): the five prompt builders, the prompt-input schemas, `NO_PRIOR_HISTORY_SUMMARY`, `WorkflowLlmStep`, and the dead summary types all have the deleted packages as their only consumers and are removed (the Cloudflare workflow builds its prompts inline). In the same pass, the workflow's deep relative imports into `services/domain/src` and `services/db/src` are normalized to package imports so the eslint boundary rule binds again. The OpenAPI document already describes only the Cloudflare trigger route and needs no change.
- **Test adaptation without new tests:** The test helper that seeded plans through the internal HTTP endpoint is reworked to seed through the remaining plan repository function directly, keeping the public API test suite green; the testkit's other internal-endpoint helpers (internal headers, complete-week, create-next-week, day-patch, mark-all-days) are deleted with it, as is the public suite's `/internal/*` 403 case. The lifecycle integration test file is deleted outright (agreed: its public-behavior side coverage is acceptably lost; core logic remains covered at the repository layer).
- **UI feature removal:** The "Generate plan" button component is deleted and removed from the week heading; the dead commented reference in the tracker page empty state is removed, and the empty-state copy stops advertising plan generation (story 17). The legacy workflow client functions and the polling utility are deleted with their tests. Two pieces of UI code orphaned by the removal go with it: the store's `refreshTracker` action (its only live caller was the button) with its tests, and the inert complete-week cooldown utility (its starter exists only in commented-out code) with its test. The "Complete week" button keeps its current Cloudflare implementation, minus commented-out legacy imports and the commented logic blocks that referenced the deleted polling utility.
- **Config and docs:** Docker Compose for workflows and the workflows env files are removed, along with the root `.dev.vars.example` (which is entirely worker-scoped); Temporal, tunnel, and internal-service variables in the API env example are scrubbed. Tooling references to both deleted packages are removed: task-runner tasks (`dev:api`, `dev:worker`, `docker:build`), the root `package.json` eval scripts, lint boundary rules, the root `tsconfig.json` project references, `pnpm-workspace.yaml` build allowances, and the CI exclusion comment. The Worker's `wrangler.jsonc` drops the `/internal/*` route pattern, and the committed generated `worker-configuration.d.ts` is regenerated after the env scrub (dropping the `BRAINTRUST_*`, `INTERNAL_API_*`, and `WORKFLOW_*` types). The API's unused `openai` dependency and the empty `src/agent/index.ts` file are removed. README and architecture/operations docs are updated to describe only the Cloudflare architecture — including the monorepo-structure doc's agent sections and dependency graph, the evals doc (rewritten to describe the future re-wiring, or removed), the POC-era `system_design.md`, and the stale forward-references in `docs/future_state_after_mvp/`. The in-progress doc `docs/in_progress/api_env_wrangler_types.md` tracks exactly this cleanup and is closed out. Historical migration issues and bug reports are left untouched as the project record.

## Testing Decisions

- **No new tests.** The user explicitly decided testing the Cloudflare workflow (its route, step functions, and orchestration branching) is out of scope for this pass, and no workers-pool test tooling will be introduced.
- **What remains must stay green:** the existing suites for the public API, the remaining persistence repositories, the remaining domain contracts, and the UI. A good test here is one that exercises external behavior (HTTP responses, repository results) rather than internals — matching the existing style of the public API and repository test suites.
- **Deletions, not rewrites:** tests that exclusively cover deleted surfaces are deleted: the entire worker package suite, the legacy agent package suite, the API proxy tests, the lifecycle tests, the internal-command repository tests (including `plan-generation-context.test.ts`), removed-contract and coach-prompt schema tests, the UI workflow client/polling tests, the `refreshTracker` store tests, the complete-week cooldown tests, and the public API suite's `/internal/*` 403 case.
- **Prior art for the one adaptation:** seeding test state through repository functions directly already exists in the API test suite (a test that adjusts week dates through the test database handle), so the reworked seeding helper follows an established pattern rather than inventing one.

## Out of Scope

- Testing the Cloudflare workflow in any form (route tests, step-function tests, orchestration tests, workers-pool setup).
- Rebuilding on-demand plan generation on Cloudflare Workflows (returns later as its own feature; new clients cannot get a first plan through the UI in the interim).
- Changing the authentication posture of the workflow trigger route.
- Removing or rewriting historical migration issues or bug-report documents.
- Any change to the Cloudflare workflow's logic, prompts, retry policy, or step structure.

## Further Notes

- The deletion is safe because the Cloudflare workflow never calls the internal HTTP surface: it invokes persistence functions directly. The two systems share only the domain contracts for generated plans, which are retained.
- Local secret files that are git-ignored are cleaned of stale entries as part of this work; no deployed secret changes are required beyond what the platform dashboard already holds.
- After the package deletions, the package manager lockfile is regenerated to prune Temporal, Braintrust/eval, and legacy-agent dependencies.
- Verification gate before merge: clean install, lint, typecheck, full test suite, and a Worker dry-run deploy must all pass.
